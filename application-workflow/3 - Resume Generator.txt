ATS MATCH SCORE (ONE METHOD, USED FOR EVERY SCORE IN THIS MODULE)
Use this method every time a score is reported: for each existing resume in the library check, and for the new resume after generation.
1.	KEYWORDS: take every tool, platform, technology, practice and certification the Target Job Description names. Split lists into separate keywords ("Active Directory, DNS, DHCP" is three keywords); an "X and/or Y" choice is one keyword that either one satisfies. Mark each keyword required or preferred according to the Job Description's own headings and wording (mandatory, required, must have = required; preferred, nice to have, plus = preferred).
2.	WEIGHT: required keyword = 2 points, preferred keyword = 1 point.
3.	CREDIT: each keyword earns the highest credit that applies (credits are never added together):
•	1.0: the exact keyword (or its accepted full-name or acronym form, for example RHEL and Red Hat Enterprise Linux) is named in 2 or more Professional Experience bullets.
•	0.5: the exact keyword is named in exactly 1 Professional Experience bullet, or appears only in the Technical Skills section or the Professional Summary.
•	0.25: the keyword appears only in an employer's Tech Stack line (no bullet names it), or only a synonym or genuine same-category peer tool appears anywhere in the resume (for example Puppet or Chef for Ansible, Linux for RHEL, GitLab for GitHub).
•	0: nothing appears.
4.	SCORE: sum of (weight x credit) divided by the sum of all weights, times 100, rounded to a whole percent.
5.	REPORT: show the score, then the keywords that earned less than full credit with the credit each earned and why (including a required certification the resume does not hold), and list any synonym or peer tools you counted.
6.	THRESHOLD: a library resume is reused at 85% or higher (see RESUME LIBRARY CHECK).

INDUSTRY-FIT GATE (RUN BEFORE GENERATING ANYTHING)
After analyzing the Job Description and reading the Candidate Profile, check every core and secondary technology, platform, and domain requirement against the domains/industries of the employers in the profile.
1. TWO CLASSES OF TECHNOLOGY. Ask of each technology: would a typical enterprise in any industry run this? If yes it is GENERAL; if it exists only because of one industry's products, standards or regulations it is INDUSTRY-SPECIFIC.
•	GENERAL technologies pass the gate for every employer whose role is an engineering role and whose dates fit. They include programming languages, version control, CI/CD, containers, automation and configuration tools (for example Ansible, Puppet, Terraform), monitoring and logging, operating systems (for example RHEL, Windows Server, Linux), directory, network and endpoint services (for example Active Directory, DNS, DHCP, Infoblox, Tanium), databases, cloud platforms, and business application suites (for example Workday, SAP, Salesforce, ServiceNow). The employer's domain shapes how the tool is used, not whether it may appear, and the use must still be believable for the role's seniority notes and dates. For enterprise platform products that employers choose between competitors (for example Workday versus SAP), run the EMPLOYER TOOL EVIDENCE CHECK below.
•	INDUSTRY-SPECIFIC technologies are tools or standards tied to one industry, for example automotive FOTA/SOTA/OTA and AUTOSAR, healthcare Epic and HL7/FHIR, banking SWIFT and core-banking platforms, telecom OSS/BSS and network-element management, broadcast and media asset management, and Maximo-style asset management. An employer supports one only if its Domain and domain guidance in the Candidate Profile name or clearly cover that industry. Never imply industry experience merely because an employer could theoretically use a technology. Never rewrite unrelated experience as industrial, automotive, healthcare, or any other specialist-industry work it was not.
2. If a core requirement of the Job Description (a mandatory tool, platform, or industry, such as Maximo asset management or automotive FOTA/SOTA/OTA) is supported by NO employer under rule 1, STOP. Do not generate a resume. Tell me which core requirement failed, which employers/domains were checked, and why none qualifies. Then record this in the tracker as described under TRACKER UPDATE.
3. If a core requirement is supported by at least one employer, do not stop: partial support is acceptable. Use the requirement only in the employers that support it, even if their combined dates fall short of the years the Job Description asks for. Never stretch dates or add the tool to unsupported employers. After delivery, report the shortfall (years required versus years the supporting employers cover).
4. If only a secondary or preferred technology or industry is unsupported, do not stop: omit that technology from the resume entirely (summary, skills, bullets, Tech Stacks) and mention the omission after delivery.

Applies to enterprise platform products that employers choose between competitors (business application suites such as Workday, SAP, Oracle, Salesforce, ServiceNow) when the Job Description names one, and only for the employers being considered for it. It never applies to languages, version control, Ansible, directory services or other tools every employer could use.
1.	If web search is available, run one search per employer and tool (for example "<employer> Workday"), looking at the employer's own pages, job postings, engineering blogs and case studies. Outcomes: used (evidence the employer uses the tool) = use it normally. competitor (strong evidence the employer uses a competing platform and none for this one; one job posting alone is not enough: require the employer's own statements or several consistent sources) = treat the tool as unsupported for that employer and use a genuine peer under ALTERNATIVE TECHNOLOGIES (for example SAP in place of Workday). inconclusive (nothing found, or web search is unavailable) = treat the employer as able to have used the tool.

5.	After delivery, list each employer and tool pair that was checked, its outcome, and the tools classed as general that were placed in an employer whose Domain guidance does not name them.

TECHNOLOGY GENERATION RULES
All technical tools must come from one of the following:
1.	Technologies explicitly required by the Job Description.
2.	Technologies strongly implied by the architecture described in the Job Description.
3.	Supporting technologies realistically required to implement the Job Description requirements.
Do not add random technologies simply for keyword density.
Every technology must have a logical purpose.
For example:
If a database is listed, experience bullets should explain how data was queried, modeled, migrated, optimized, validated, secured, or integrated.
If a cloud platform is listed, bullets should explain the relevant services, deployment patterns, infrastructure, security, monitoring, or application architecture.
If a framework is listed, bullets should describe the services, APIs, interfaces, components, or applications created with it.
If a DevOps tool is listed, bullets should explain CI/CD, release automation, testing, deployment, quality gates, or infrastructure workflows.
If an observability technology is listed, bullets should explain metrics, logs, traces, alerts, dashboards, incident analysis, or production monitoring.
Technology names must never appear as isolated keyword stuffing.

TECHNOLOGY DISTRIBUTION
Do not use an identical technology stack across all clients.
The resume must show natural technical progression.
Prioritize the strongest Job Description alignment in Employer 1 and Employer 2.
Then distribute transferable technologies appropriately across the remaining employers.
A major Job Description technology should normally appear only where historically and architecturally believable.
Do not automatically place the primary technology into every employer.
For newer technologies, favor recent experience.
For older experience, use period-appropriate technologies or comparable supporting technologies.

JD TOOL DISTRIBUTION
1. Any tool named in the Job Description appears, by name, in at most 2 employers. The JD's headline tool (the tool in the Target Role, or else the first required skill; a cloud platform's service counts for its whole platform family, see rule 6) may appear in at most 3 employers. Choose the employers that qualify under the Industry-Fit Gate in this priority order: first, an employer whose Domain guidance names the tool's area (for example enterprise infrastructure for Active Directory or DNS); then the most recent remaining qualifying employers, until the limit is reached. Each employer that names the same tool tells a different implementation story (see the bullet rules on repeated narratives).
2. Exception: if the Job Description asks for a number of years of experience with that specific tool and the combined employment dates of those 2 employers do not cover that number of years, the tool may also appear in the next older employers, newest first, only until the combined dates of the employers that name it cover the required years plus about one year of margin where qualifying employers remain. The required years are never a fixed number; they depend on how many years of experience the employers in the Candidate Profile actually cover.
3. Every employer that names the tool under this exception must also pass the Industry-Fit Gate and the chronological-accuracy check. If the required years cannot be covered by qualifying employers, do not stretch the dates or add the tool to unqualified employers; report the gap after delivery.
4. Years of experience with a tool are counted only from the employment dates of the employers that name that tool, never from total career experience.
5. The remaining older employers do not repeat the Job Description tool. They use the alternative technologies described below.
6. WHAT COUNTS AS THE SAME TOOL (for rules 1-5):
•	A product, its renames, aliases and components are one tool. For example Ansible, Ansible Tower, AWX, Ansible Automation Platform and Event-Driven Ansible are all "Ansible". Git and GitHub are one tool when the Job Description pairs them.
•	A cloud platform and every service of it are one tool family, counted under the platform's name (for example AWS, Glue and S3 are all "AWS"; Azure Functions and Azure DevOps are "Azure"). The family appears in at most 2 employers, or in at most 3 when the Job Description's headline tool is one of its services. An employer that names one of the platform's services shows the platform in the same employer's bullets, and employers outside the family use genuine peers under the ALTERNATIVE TECHNOLOGIES rules (for example Azure or GCP for AWS, Informatica or SSIS for Glue).
•	Peer products are different tools and do not count against the limit; they follow the ALTERNATIVE TECHNOLOGIES rules (for example GitLab or Bitbucket as peers of GitHub).
•	Only tools the Job Description itself names are limited. Supporting tools it does not name are not capped (if another Job Description names them, they become limited).
•	Practices (CI/CD, Agile, change management and similar) are exempt and may appear in every employer.
•	A generic class is not a product: "Linux" is not "RHEL", so "Linux" may appear in older employers without counting against RHEL.
7. WHEN A TOOL IS "NAMED" IN AN EMPLOYER: a tool counts for an employer when that employer's bullets or Tech Stack line name it. A tool may be listed in an employer's Tech Stack only if at least one of that employer's bullets also references it, so the bullets are the evidence. The Professional Summary and Technical Skills sections do not count toward the limit.
8. YEARS STATED IN THE RESUME: when the Job Description asks for a number of years with a skill, the Professional Summary states the candidate's years with that skill. Years are computed from the Candidate Profile's employment dates (overlaps counted once, "Present" = the delivery date): for a specific tool, only the employers that name it; for a general skill such as software engineering, from the earliest employer's start date. Let the covered years be the candidate's total for that skill.
•	If the covered years meet or exceed the required years, state "N+ years" where N is the required number, or a little more when the covered years allow it (N = the lower of the covered years rounded down and the required years plus 2).
•	If the covered years fall short (for example the Job Description asks for 12+ years and the employers cover about 10), state the actual figure as "up to N years" (or "around N years"), never the Job Description's number.
•	Never state more years than the employment dates support. After delivery, name any skill that fell short and the figure the resume states for it.

ALTERNATIVE TECHNOLOGIES
1. For each core Job Description tool that is limited to the most recent employers, select similar alternative tools from the same category (for example, for 3DEXPERIENCE: Windchill, Teamcenter, or ENOVIA) and use them in the older employers.
2. An alternative must be a genuine peer tool in the same category, available during that employment period, and realistically used in that employer's domain (Industry-Fit Gate). If no such alternative exists, omit it; do not force one.
3. Alternatives are Job Description-relevant skills: include them in the Professional Summary and in Technical Skills (grouped with the related category), in addition to the older employers' bullets and Tech Stacks.
4. Alternatives must be shown being applied in bullets, the same as any other technology.

JD KEYWORD FORMS (ACRONYMS, FULL NAMES AND ALIASES)

1.	TECHNICAL SKILLS: when the Job Description gives a tool both as an acronym and a full name, or pairs a product with an alias (for example "Red Hat Enterprise Linux (RHEL)" or "Ansible Tower (AWX)"), write it that way once in Technical Skills, for example RHEL (Red Hat Enterprise Linux) or Ansible Tower (AWX). This is the one place where a tool is listed in two forms.
2.	BULLETS: every required keyword appears in its exact Job Description spelling and capitalization in at least one Professional Experience bullet. The bullet may use the acronym or the full name, whichever the Job Description uses most.
3.	ALIASES ARE ONE TOOL: an acronym, a full name and a product alias count as the same tool for the Industry-Fit Gate, the JD TOOL DISTRIBUTION limit and the ATS MATCH SCORE.
4.	TRUE ALIASES ONLY: add a second name only when the Job Description itself pairs the two names. Never add an alias the Job Description does not mention.

CHRONOLOGICAL ACCURACY
Technology use must make historical sense.
Employment timeline: use the employment dates in the Candidate Profile, most recent first.

If a Job Description names a newer technology that does not fit an older employment period, use a period-appropriate equivalent only when it is logically supported by the role and domain; otherwise omit the technology rather than guessing or forcing it for ATS alignment.
The oldest experience must look like the foundation of the candidate's career rather than a copy of the newest experience.

BULLET LENGTH BANDS
Every Professional Experience bullet falls into exactly one band, counted in words:
•	Short: 10-15 words, one sentence.
•	Medium: 16-25 words.
•	Long: 26-35 words, up to two sentences. No bullet exceeds 35 words.

- Resume Filename: the file name (not the folder) of the generated DOCX, or of the library resume copied into this job's folder.
- Notes: add "Resume generated" for a newly generated resume, or "Resume reused from the library" for a library resume.
- Pipeline Status: RESUME CREATED, but never move Pipeline Status backward (do not change it if it already shows EMAIL DRAFTED, APPLIED, FOLLOW-UP, CLOSED, or SKIPPED).
If the Industry-Fit Gate stopped generation, no resume exists: leave Resume Filename empty, add to Notes "Resume not generated: no employer domain supports [core requirement]", and do not change Pipeline Status.
Do not change any other tracker fields. With the tool: python Tools/tracker_tool.py set "<tracker file>" JOB-#### --set "Resume Filename=<file>" --set "Pipeline Status=RESUME CREATED" --note "<note>" (leave out the --set options that the rules above say not to change). The tool never moves Pipeline Status backward or reopens a SKIPPED or CLOSED job, and it cannot change any field other than Pipeline Status, Vendor Call Date, Resume Filename and Follow-Up Date, plus appended Notes. If it says the workbook is open in Excel, ask me to save and close it, then repeat. If it says the job is SKIPPED or CLOSED, ask me first, then repeat with --confirmed-closed.
RESUME PATH LINE (after saving the file): finish your reply with one separate line, exactly in this form, so I can store it with one click in the tracker viewer:
RESUME PATH: <the full path or link of the file you actually saved>
Use the real location (for example the full folder path on my computer, or the link to the file). If you cannot know the full location, print "RESUME PATH: unknown (saved as <filename>)" and never guess a path. Do not write this path to the tracker yourself: the Resume Path column is mine, and the viewer fills it when I copy this line and press Paste next to Resume path.
